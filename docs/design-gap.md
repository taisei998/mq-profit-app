## この文書の位置づけ

設計書は「単一HTMLファイル（`legacy/MQ率計算アプリ.html`）から新システムへ移行する」前提で
書かれていますが、**その移行は本リポジトリで既に完了しています**。ただし設計書が推奨する
構成（Supabase）とは別の構成を採っており、また設計書が新しく足そうとしている機能
（ステータス管理・ダッシュボード等）はまだ入っていません。

そこで「設計書のどこが済んでいて、どこが残っているか」を章ごとに突き合わせたのがこの文書です。
設計書そのものは書き換えず、ズレはここに記録していく方針です。

## 2. §3 計算ロジック — 完全移植済み・テストで固定

設計書§3の式は `packages/shared/src/calc.ts` の実装と一致しています。
**設計書§6.1の必須テストケース11件は、全件を `packages/shared/src/calc.test.ts` に
テストコードとして取り込み済み**です（`npm run test` で検証されます）。

固定されている挙動:

- 端数処理は四捨五入。明細行ごとに丸めてから合算する（手数料・ポイントUPのみ合算後に丸め）
- 歩留まりは除算。空欄・0は係数1として扱う（ゼロ除算回避）
- クーポンの税抜換算は8%固定
- 販売金額の自動計算（1セット目 → 2〜5セットへ「単価×セット数」、2セット目以降は手動上書き可）
  は `applyDirectPriceInput()` として `calc.ts` に切り出し、テスト対象にしています

> リファクタでこのブロックが赤くなったら、それは仕様変更です。数値が経営判断に直結するため、
> テストの方を書き換えて通す、ということは絶対にしないでください。

### 価格・明細の持ち方が設計書と違う点（要判断）

設計書は `product_prices` / `product_price_lines` に正規化する想定ですが、現行は
`Product.normalData` / `saleData` / `couponData` の3列に、区分ごとの計算結果と明細を
**JSON文字列でまとめて保存**しています（SQLiteがJSON型に対応しないため文字列）。

- JSONのまま続ける利点: 明細の項目構成が商品ごとに可変でも素直に入る。実装済みで動いている
- 正規化する利点: 「原価が高い商品」「特定の資材を使っている商品」のような**明細をまたぐ検索・集計**ができる

現状そうした横断集計の要件は出ていないため当面はJSONのままとしますが、HOMEダッシュボードで
「原価率の推移」のような分析をしたくなった時点で再検討が必要です。

### 実データの調査結果（2026年9月16日）

決定#2・#3の裏取りのため、実際の受注・商品CSVを確認しました。

| モール | ファイル名の形 | 商品コードの列 | prefix | 数量の列 | 受注日時 |
|---|---|---|---|---|---|
| 楽天市場 | `【楽天CSV】YYYYMMDD.csv` | `商品番号` | **なし**（`wbankan4s4s_s_26_1111_1500g`） | `個数` | 注文日と注文時間が**別列** |
| au PAY マーケット | `orderdl<店舗ID>_<日時>.csv` | `itemManagementId` | `dk_` | `unit` | `orderDate` に日時が同居 |
| Yahoo!ショッピング | `Yahoo!_商品別.csv` | `サブコード` | `yk-`（区切りが `-`） | — | — |
| Amazon | `2026_07_Amazonご当地風土_在庫.csv` | `出品者SKU` | `gam_` | — | — |

分かったこと:

- **数量の意味は楽天とau PAYで一致していた。** どちらも `単価 × 数量 = 合計金額` が成立する。
  - 楽天: 商品毎税込価格 1111 × 個数 2 = 商品合計金額 2222
  - au PAY: itemPrice 1500 × unit 4 = totalItemPrice 6000 ／ 2000 × 11 = 22000
  - `unit=11` のような値が出るため、数量欄は「セット数」ではなく**個数**と考えるのが自然。
    まとめ買いは `..._1500g` と `..._500gx4` のように**別の商品コードで出品**されている。
- **prefixの規則は不揃い。** 区切り文字がモールで違い（`_` と `-`）、楽天にはprefixが無い。
  機械的にprefixを剥がして共通コードを作る方式は成立しない。
  - 例: `dk_25zakkoku_u_22_1180_450gn`（au PAY）と `yk-25zakkoku-u-22-2360-900gn`（Yahoo!）で
    本体 `25zakkoku_u_22` が共通
- **`gam_` は Amazon の出品者SKUだった。** しかもファイル名が「Amazonご当地風土」で、
  決定#5で挙がった店舗名と一致する。prefixが「モール」だけでなく
  **「モール×店舗」**を表している可能性がある。
- **設計書のモール一覧に Amazon が無い**（楽天/Yahoo!/au PAY/自社EC の4つ）。

### #6の実装（反映済み）

`aggregateOrders()` のセット選択を変更しました。

```
変更前: const idx = Math.min(qty, 5) - 1; const rate = grp.rates[idx];  // 数量3 → 3セット目の粗利率
変更後: const rate = grp.rates[0];                                       // 常に1セット目の粗利率
```

売上金額は従来どおり `単価 × 個数`（またはCSVの合計金額欄）なので、粗利は個数に比例します。
この挙動は `packages/shared/src/orders.test.ts` の
「数量は個数として扱い、常に1セットの粗利率を適用する」でテスト固定しました。

> **副作用**: 商品登録の「2〜5セット」の入力欄は、粗利集計では使われなくなりました。
> まとめ買い商品は別コードで1セットとして登録されるためです。
> 入力欄自体は「まとめ買いにしたらいくらになるか」の検討用として残していますが、
> 不要であれば削れます（#11として確認中）。

### #12の実装（反映済み）

`matchKindByPrice()` を「最も近い区分を採用」から「**一致した区分だけを採用**」に変更しました。
一致しなかった行は集計から除外し、内訳を `priceMismatchDetail`（`商品コード @単価` → 件数）に残します。
値下げ直後などで価格が合わない受注を、気づかないまま誤った粗利率で集計してしまうのを防ぐためです。

> **運用上の注意**: この変更で未紐付け件数は増えます。モールの価格を変えたら
> 商品マスタ側も更新しないと、その商品の受注がまるごと集計から外れます。
> 未紐付け一覧の画面（設計書§5.1のアラート）を早めに用意した方がよさそうです。

### Amazon注文レポートの調査結果（2026年9月16日）

実ファイル（65行）を解析しました。**他モールと形式が大きく異なります。**

| 項目 | 内容 |
|---|---|
| 形式 | **タブ区切り・拡張子 `.txt`**（カンマ区切りではない）、Shift_JIS、31列 |
| 受注日 | `purchase-date` = `2026-09-14T23:57:59+09:00`（ISO8601・タイムゾーン付き） |
| 商品コード | `sku`（出品者SKU）。`asin` も併記されている |
| 数量 | `quantity` |
| 金額 | `item-price` = **税込の合計金額**（単価ではない）。`item-tax` はその内数の消費税 |
| 割引 | `item-promotion-discount` / `ship-promotion-discount` |
| 状態 | `order-status` = `Pending` 46件 / `Shipped` 15件 / **`Cancelled` 4件** |

検証したこと:

- `item-price` が税込なのは内税から確認できる（2495 × 8 ÷ 108 = 184.8 ≒ `item-tax` 185）
- 数量2の行は `item-price` 4990 = 2495 × 2。**単価の列が存在しない**
- **`gam_` で始まるSKUは41行だけで、残り24行はprefixが無い**
  （`AK-LG6I-LKWB` `9P-RR9C-EQYJ` など、Amazonの自動採番SKU）

対応済み:

- CSVパーサに区切り文字の自動判定（`detectDelimiter()`）を追加し、タブ区切りを読めるようにしました。
  ファイル選択も `.csv` に加えて `.txt` / `.tsv` を受け付けます
- `toDateKey()` はISO8601形式（`T` 区切り・タイムゾーン付き）にもそのまま対応しています
- 実ファイルで確認済み: タブ区切りと判定 → 31列 → 65行 → 全件 `2026-09-14` に集約

### #15・#16の実装（反映済み）

`OrderColumnMapping` に3つの設定を追加しました（いずれも任意項目なので、既存モールの取込は挙動が変わりません）。

| 設定 | 内容 |
|---|---|
| `unitMode` | `'column'`（既定・単価の列を使う）／ `'divide'`（支払い金額 ÷ 数量で単価を出す） |
| `statusCol` | 注文ステータスの列。`-1` は「使わない」 |
| `excludeStatuses` | 集計から除外する値の配列（大文字小文字は区別しない） |

除外はコード照合や売価照合より**先に**行います。キャンセル行を「未紐付け」として数えてしまうと、
対応が必要な件数に見えてしまうためです。集計結果には除外の内訳
（`excluded` / `excludedDetail`）が入り、画面にも理由別に表示されます。

**Amazonの注文レポートは列の自動認識に対応しました。** 見出しに `amazon-order-id` と `sku` があれば、
`purchase-date` / `sku` / `item-price` / `quantity` / `order-status` を自動であて、
単価の取り方を「支払い金額 ÷ 数量」、除外する値を `Cancelled` に設定します。

```
除外の内訳: 商品が未登録 1件 ／ 売価不一致 1件（@2200） ／ Cancelled 1件
```

### 受注データの永続化・取込履歴・列設定の保存（2026年9月16日）

### ジョブカンワークフロー連携（2026年9月18日）

**決定 #18: 稟議の状態はジョブカンから自動で取り込む。突き合わせは「稟議タイトルに商品IDを入れる」運用で行う。**

設計書§2.2では稟議フローをアプリ内で完結させる案もありましたが、実際の承認は
ジョブカンワークフローで回っています。これまでは「ジョブカンで承認 → 誰かがこのアプリで
手動でステータスを変える」という二度手間になっていたため、そこを自動にしました。

**調べて分かったこと（ジョブカン経費精算/ワークフローAPI β版）**

| | |
|---|---|
| 申請書の取得 | `GET /wf_api/v2/requests/` … ステータス・フォーム・申請者・期間で絞り込み可 |
| **申請書の作成** | **できない**（`POST` が無い） |
| 認証 | `Authorization: Token <トークン>`（`Token` は literal） |
| トークン発行 | **Admin・管理者権限のアカウントのみ。発行者の権限が外れると無効化される** |
| 上限 | 5,000回/時・1ページ100件 |
| Webhook | 無し（こちらから取りに行く） |

**この結果、アプリから申請を出すことはできません。** 申請・承認はジョブカンのまま、
このアプリは「今どの段階か」を写し取るだけ、という関係は変わりません。
2026-09-17に「ステータス変更は誰でも可」とした判断とも整合します。

**突き合わせ方**

ジョブカン側にこのアプリの商品を指す項目が無いため、**稟議のタイトルに商品ID（`A0123`）を
含める運用**にしました（正規表現 `A\d{4,}` で読み取り）。フォームに専用項目を追加する案より、
既存の申請書を変えずに始められる点を取りました。

**取り込み方針**

- 承認完了→承認済み、否決→却下。**差戻し・完了後取消はアプリ側の状態を動かさない**
  （戻すかどうかは人の判断。ジョブカン側の生の状態は `jobcanStatus` に残す）
- **「販売中」「販売終了」の商品は稟議の状態で巻き戻さない**（販売開始後の事故防止）
- 「下書きのまま承認された」場合は draft → pending → approved と2段で動かす
  （`enforce_status_transition` の順序制限を壊さないため）
- ジョブカンのAPIには「更新順で取る」条件が無いので、**直近90日ぶんの申請書を毎回取り直す**

**置き場所**

ブラウザから直接ジョブカンを叩くと、公開されているJSにAPIトークンが埋まってしまいます
（社内の稟議を全部読める鍵になります）。そのため Supabase Edge Function
（`supabase/functions/jobcan-sync`）に置き、トークンはSupabaseのシークレットに保存します。
費用は無料枠の範囲内です。手順は [docs/jobcan.md](jobcan.md)。

**あわせて直したもの**

`touch_updated_by` が `auth.uid()` をそのまま入れていたため、仕組みによる更新（同期処理）で
**更新者がnullに上書きされる**状態でした。`coalesce(auth.uid(), old."updatedBy")` に変更し、
前回の更新者を残すようにしています。
