# 旧版（Supabase）からのデータ引継ぎ

公開申請で「既存データの投入：要」としたための仕組みです（決定 #21、`docs/design-gap.md`）。
**実際に新しいデータベースへ流すのはDXです。** こちらは「そのまま流せば正しく入るSQL」を渡します。

## 流れ

```
旧版のSupabase ──①書き出し──▶ export.csv ──②変換──▶ export_import.sql ──③DXが流す──▶ 新しいデータベース
```

**書き出したファイルと変換後のSQLには、原価や受注などの業務データが入ります。
このリポジトリは公開されているので、ここに置かないでください。**（`.gitignore` でも弾いています）

### ① 書き出す（Supabaseの画面で）

1. https://supabase.com/dashboard → `mq-profit-app` → 左メニューの **SQL Editor**
2. [`export_from_supabase.sql`](export_from_supabase.sql) の中身を貼り付けて **Run**
3. 結果の右上の **Export → Download CSV** で保存する

読み取るだけなので、旧版のデータは一切変わりません。

### ② 変換する

```bash
node db/legacy/convert.mjs <保存したCSV> [出力先.sql]
```

件数が表示されるので、旧版の画面で見える件数と合っているか確認してください。

### ③ DXへ渡す

変換後のSQLを、**マイグレーション（`migrate`）を流し終えた新しいデータベース**に1回流してもらいます。

- 1つのトランザクションで入るので、途中で失敗したら全部取り消されます
- 間違えて2回流しても、同じものが二重に入ることはありません
- 最後に表ごとの件数が出るので、②で表示された件数と一致すれば成功です

## いつやるか

**新しい公開版へ切り替える直前**に行います。早くやりすぎると、その後に旧版で登録・取込した分が漏れます。

1. 旧版の利用を止めてもらう（「この時間以降は旧版を触らないでください」と連絡）
2. ①〜②を行い、DXへ渡す
3. DXの投入が終わったら、新しい公開版のURLを案内する

## 変換で吸収していること（そのまま入れると壊れる点）

| 問題 | 対処 |
|---|---|
| 登録者・更新者・取込者のIDが旧版（Supabase）のもので、新しい社内認証の利用者とは別物 | **空にする**。新しい方で最初にログインした時点から記録が始まる |
| 新しいデータベースはマイグレーションで5つのモールを**別のID**で作る | **モール名で突き合わせ**て店舗・列設定を付け替える |
| 商品の固有ID（A0001…）の続き番号が1から始まる | **取り込んだ最大値の次**に合わせる。合わせないと次の新規登録が番号の重複で失敗する |
| 旧版にしか無い列がある場合 | 新しい方にある列だけを移し、残りは捨てる |

## 確認済みのこと（2026-10-09、本物のPostgreSQLで）

- 店舗→モールの付け替え、列設定→モールの付け替え（旧版にしか無いモールも含む）
- 登録者・取込者が空になること
- 円記号・引用符・改行・タブ・絵文字・`$` が**1バイトも変わらず**入ること（名前と、明細のJSONの中の両方）
- 受注2,500件の金額の合計が一致し、HOMEの集計（`dashboard_summary`）が動くこと
- 次に登録した商品が、取り込んだ最大番号の次（A0012の次はA0013）になること
- 2回流しても二重に入らないこと
