# ジョブカンワークフロー連携

粗利稟議はジョブカンワークフローで回しています。このアプリはその**結果を写し取る**だけです。

```
ジョブカンで承認  →（15分おきに取得）→  商品のステータスが自動で「承認済み」になる
```

## できること・できないこと

| | |
|---|---|
| 稟議の状態を取ってくる | **できる** |
| 承認／否決を商品ステータスに反映する | **できる**（自動） |
| **このアプリから稟議を申請する** | **できない** |
| 承認・否決の操作をする | **できない** |

ジョブカンのAPIは**参照専用（GETのみ）**です。申請と承認は従来どおりジョブカンで行います。
APIは**β版**のため仕様が変わる可能性がありますが、読むだけなので、
壊れても「自動反映が止まる＝今までどおり手動」に戻るだけです。業務は止まりません。

## 運用の約束：稟議のタイトルに商品IDを入れる

ジョブカンの稟議とこのアプリの商品を結びつける鍵です。**これが無いと連携しません。**

```
【粗利稟議】A0123 熊本県産あさり 500g
              ~~~~~ これ
```

- 商品ID（`A` ＋ 数字4桁以上）はこのアプリが自動で振ります。商品一覧・詳細で確認できます
- タイトルのどこに入れても構いません。前後に文字があっても読み取れます
- 1つの稟議に複数の商品IDを書けば、まとめて反映されます
- 同じ商品に複数の稟議がある場合は、**新しい方**を採用します

## ステータスの対応

| ジョブカン | このアプリ |
|---|---|
| 申請中（in_progress） | 稟議中 |
| 承認完了（completed） | 承認済み |
| 否決（rejected） | 却下 |
| 差戻し（returned） | **変えない**（記録だけ残す） |
| 完了後取消 | **変えない**（記録だけ残す） |

差戻しで自動的に下書きへ巻き戻さないのは、**戻すかどうかは人の判断**だからです。
ジョブカン側の状態は商品の `jobcanStatus` に残るので、画面で理由を説明できます。

**すでに「販売中」「販売終了」になっている商品は、稟議の状態では動かしません。**
販売が始まったあとに巻き戻ると事故になるためです。

## 設定手順

### 1. ジョブカンでAPIトークンを発行してもらう

**管理者権限（Admin・管理者）のアカウントでしか発行できません。**

> 右上のお名前 → **会社情報設定** → **共通ID連携・API管理** タブ → **発行する**

**発行してもらうアカウントに注意してください。**
ジョブカンの仕様で、**トークンを発行したアカウントの権限がAdmin・管理者から外れると、
そのトークンは無効になります**。異動や退職で連携が止まらないよう、
管理部門や情シスの「権限が変わらないアカウント」で発行してもらってください。

### 2. 粗利稟議のフォームIDを調べる

トークンが手に入ったら、コマンドで一覧を取れます（`トークン` は実際の値に置き換えてください）。

```bash
curl -H "Authorization: Token トークン" "https://ssl.wf.jobcan.jp/wf_api/v1/forms/"
```

返ってきた中から粗利稟議のフォームを探し、その `id` を控えます。
指定しなくても動きますが、**全フォームを取りに行くので必ず指定してください。**

### 3. Supabaseにトークンを登録する

**Edge Functions → Secrets**（または Project Settings → Edge Functions）で登録します。

| 名前 | 値 |
|---|---|
| `JOBCAN_API_TOKEN` | 手順1のトークン（**必須**） |
| `JOBCAN_FORM_IDS` | 手順2のフォームID。カンマ区切りで複数可 |
| `JOBCAN_LOOKBACK_DAYS` | 何日前の申請までさかのぼるか（未設定なら90） |

> トークンはここにしか置きません。**画面のコードにもリポジトリにも入れないでください。**
> 入れると、社内の稟議を全部読める鍵を公開することになります。

### 4. テーブルを用意する

SQL Editor で、この順に実行します。

1. `supabase/01_schema.sql` （更新者が消えないようにする修正が入っています。**再実行が必要**）
2. `supabase/04_jobcan.sql`

### 5. 関数を配置する

```bash
npx supabase login
npx supabase link --project-ref cqzvuuwwzcjgbtcfnvdt
npx supabase functions deploy jobcan-sync
```

手で動かして確かめます。

```bash
curl -X POST "https://cqzvuuwwzcjgbtcfnvdt.supabase.co/functions/v1/jobcan-sync" \
  -H "Authorization: Bearer ここにanonキー"
```

```json
{ "ok": true, "fetched": 42, "matched": 12, "updated": 3, "unmatched": 30, "problems": [] }
```

- `fetched` … ジョブカンから取れた申請書の数
- `matched` … タイトルから商品IDを読み取れた数
- `updated` … 実際にステータスが変わった数
- `unmatched` … 商品IDが書かれていない／該当商品が無い数
- `problems` … 動かせなかった商品とその理由

`unmatched` が多いのは異常ではありません。粗利稟議以外の申請書も混ざるためです
（フォームIDを指定すれば減ります）。

### 6. 定期実行にする

Supabaseの左メニュー **Integrations → Cron**（または Database → Cron Jobs）で、
`jobcan-sync` を **15分おき**（`*/15 * * * *`）に呼ぶジョブを作ります。

## 困ったとき

**動いているか確認する** … 最後の実行結果は `jobcan_sync_runs` テーブルに残ります。

```sql
select * from public.jobcan_sync_runs order by "startedAt" desc limit 10;
```

| 症状 | 原因 |
|---|---|
| `401 Invalid token header` | ヘッダの書式。`Authorization: Token 値` の **`Token` はそのまま書く文字列**です |
| 急に全部失敗し始めた | トークンを発行したアカウントの権限が外れた可能性があります（手順1の注意） |
| `updated` がいつも0 | 稟議のタイトルに商品IDが入っていないか、フォームIDの指定が違います |
| 古い稟議が反映されない | `JOBCAN_LOOKBACK_DAYS` を伸ばしてください。**申請日**でさかのぼる方式です |

### なぜ「申請日でさかのぼる」方式なのか

ジョブカンのAPIには「最後に更新された順」で取る条件がありません。
そのため、**直近90日ぶんの申請書を毎回まとめて取り直して現状に合わせる**方式にしています。
上限は1トークンあたり5,000回/時、1ページ100件なので、この頻度なら余裕があります。

### なぜブラウザから直接ジョブカンを叩かないのか

この画面はGitHub Pagesで配信される静的サイトで、**JSは誰でも読めます**。
トークンを画面に埋めると公開することになるため、Supabase側（Edge Function）に置いています。
そもそもCORSでも弾かれます。
